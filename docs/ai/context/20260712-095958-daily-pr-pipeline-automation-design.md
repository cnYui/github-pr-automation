# 每日 PR 机会流水线自动化设计

## 目标

在固定本地主控仓库中每天独立运行一次完整流水线：恢复未完成运行、扫描候选、执行 live preflight、实现最小改动、验证、提交并创建 PR。

## 现状判断

- 扫描、执行、编排三个 Skill 已存在，流水线曾真实创建 2 个 PR。
- `data/pipeline` 已提供候选快照、租约、运行恢复和跨日去重，必须使用固定本地项目，不能使用临时 worktree。
- 当前 `cnyui-pr` 自动化负责已提交 PR 的反馈与 CI 跟进，不应混入机会扫描和新 PR 创建职责。
- 当前流水线测试与类型检查通过，且没有未完成运行。

## 调度设计

- 新增独立 cron：`每日 GitHub PR 机会流水线`。
- 每天日本时间 09:00 运行，绑定 `D:\CodeWorkSpace\github-pr-automation`。
- 每轮遵循仓内 `github-run-pr-opportunity-pipeline` Skill，最多创建 `config/pipeline.json` 规定的 2 个 PR。
- 开始时先恢复未完成运行；没有未完成运行时才刷新日期报告并启动新运行。
- 只处理 live preflight 通过的候选，禁止自动 merge。
- 结束时必须关闭执行窗口并释放租约；异常退出保留状态供下一轮恢复。

## 职责边界

- 新自动化：发现机会、实现、验证、创建 PR。
- `cnyui-pr`：跟踪已有 PR 的 review、CI、评论和后续修复。
- 人工介入：CLA、账号授权、付费服务、密钥、维护者权限、产品方向和高风险大改。

## 风险控制

- 扫描启发式只能产生候选，不能替代默认分支修复状态、重复 PR 和贡献门禁复核。
- 固定每天一次并限制每轮 2 个 PR，避免质量下降和 GitHub 账号行为过密。
- 自动化提示词明确禁止覆盖用户未提交改动、禁止虚报验证结果、禁止自动合并。
- 已知扫描 CLI、API 韧性和 lease heartbeat 问题后续应继续修复，但现有状态恢复和 4 小时租约足以支撑低频试运行。
