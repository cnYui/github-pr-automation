# GitHub 项目发现 Skill 设计

## 背景

当前仓已经有日报看板、扫描器和 `public/reports/latest.json` 报告链路，但原始方向更偏“热门项目日报”。本次目标不是再做一个只看热度的榜单，而是把“找到值得后续提交低风险 PR 的 GitHub 项目”沉淀成一个可重复调用的 Codex Skill。

用户已确认以下边界：

- Skill 目标优先级是“适合后续提 PR 的低风险项目”，不是单纯热门项目。
- 默认产物同时包含：
  - 对话内候选列表。
  - 在当前仓中可落盘的看板 JSON 刷新。
- 默认候选池以 GitHub 全网搜索为主。
- 过大、明显本地跑不动、无法验证的项目默认不值得推荐。
- 大项目只有在切口属于文档、示例、坏链、配置说明等低风险改动时才保留。

## 目标

创建一个混合型 Skill：`github-daily-pr-opportunity-scan`。

它在任意目录都可以完成“搜索 GitHub 项目并给出可贡献候选”的工作；如果当前目录正好是本仓，则进一步复用现有扫描器和报告 schema，刷新 `public/reports/latest.json` 供当前看板展示。

## 非目标

- 不自动 fork。
- 不自动提交。
- 不自动打开 PR。
- 不为了凑数量降低门槛。
- 不把高 Star 或高热度直接等价成“值得投入”。
- 不把本仓已有扫描器硬绑成 Skill 唯一运行环境。

## 推荐方案

采用混合型 Skill，而不是纯仓库绑定型或纯自包含型。

原因：

- 仓库绑定型只能在本仓里用，复用性太低。
- 纯自包含型会复制当前扫描器能力，后续维护容易漂移。
- 混合型能把“候选发现与筛选规则”抽成通用流程，同时保留本仓现有看板链路。

## 运行模式

### 模式一：通用发现模式

当用户在任意目录调用 Skill 时：

1. 用 GitHub 全网搜索建立候选池。
2. 做基础去重和贡献可行性筛选。
3. 输出 5 到 10 个候选仓库。
4. 为每个候选附上推荐等级、建议切口、主要风险和验证路径说明。

此模式不依赖当前仓代码，也不要求刷新 JSON 看板。

### 模式二：看板刷新模式

当 Skill 发现当前目录存在本仓特征文件时，除通用发现模式外，再执行一层本仓集成：

- 检测信号：
  - `src/scanner/cli.ts`
  - `src/scanner/scan-runner.ts`
  - `public/reports/latest.json`
- 优先复用本仓既有扫描器、schema 和输出路径。
- 将结果同步到 `public/reports/latest.json`，必要时再同步相关静态产物。

此模式的职责仍然是“生成和刷新报告”，不是直接进入上游 PR 提交流程。

## 输入

Skill 支持以下输入，均为可选：

- `topics`
- `languages`
- `candidateLimit`
- `dateRange`

如果用户未提供，走默认模板：

- 搜索范围：GitHub 全网搜索。
- 语言：优先 AI agent、MCP、CLI、开发工具相关常见语言，不强制只限单一语言。
- 候选数：先宽搜，再收敛到 5 到 10 个对话输出候选。
- 时间范围：优先近期活跃项目，而不是历史高 Star 老项目。

## 搜索源

主搜索源：

- GitHub 全网 repository search。

补充信号：

- GitHub Trending。
- `cnYui` 的 starred repositories。
- 当前仓已有历史日报。

约束：

- 主排序和主筛选逻辑以 GitHub 全网搜索结果为主。
- Trending 和 starred 只作为补充信号，不作为主排序依据。

## 筛选与去重

### 基础去重

- 先按 `owner/repo` 去重。
- 对同一仓库的多个 query 命中结果合并信号，不重复展示。

### 重复机会去重

对每个候选仓库继续检查：

- 是否已有相关 open issue / open PR 已覆盖该方向。
- 当前问题是否其实已经在 `main` 修复。
- 是否已有维护者明确拒绝或要求先走 issue 讨论。

若已明显重复，默认降级为 `跳过` 或从候选集中移除。

## 硬门槛

以下条件默认直接降级或跳过：

- `archived` 仓库。
- 长期无维护活动的仓库。
- 本地明显无法验证的仓库。
- 依赖重型云资源、专有账号、企业内网或多机集群才能验证的仓库。
- 需要高门槛环境，且没有低风险局部切口的仓库。

唯一例外范围：

- 文档修复。
- 示例补全。
- 坏链修复。
- 配置说明修正。

即使是例外范围，也必须满足“改动价值明确、范围小、验证路径清楚”。

## 推荐等级

Skill 输出分三层：

### 值得继续

满足以下特征：

- 切口明确。
- 风险低。
- 验证路径清楚。
- 没有明显重复 PR。
- 不需要超出本地能力的大环境投入。

### 谨慎

适用场景：

- 方向可能成立，但验证成本偏高。
- 维护者门禁较重。
- 需要进一步确认是否重复。
- 本地只具备部分验证条件。

### 跳过

适用场景：

- 大概率本地跑不动。
- 需要专有资源或复杂基础设施。
- 重复风险高。
- 维护活跃度不足。
- 贡献门槛和收益不成比例。

## 推荐切口范围

优先推荐：

- 文档缺口。
- 示例缺口。
- 测试补充。
- 小 bug 修复。
- CI、lint、typecheck 等已有失败信号的小切口修复。

默认不推荐：

- 纯格式化。
- 批量拼写。
- 与项目方向无关的蹭热度变更。
- 无明确价值或无验证路径的大规模重构。

## 输出

### 对话内输出

每次默认输出 5 到 10 个候选，字段至少包含：

- `owner/repo`
- 项目简述
- 推荐等级
- 建议切口
- 关键证据
- 主要风险
- 本地验证可行性说明

### 仓内报告输出

如果当前目录是本仓：

- 刷新 `public/reports/latest.json`
- 保持与现有 schema 兼容
- 报告重点仍是“是否值得继续推进”，而不是单纯热度排行

## Skill 结构

推荐目录结构：

```text
github-daily-pr-opportunity-scan/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── references/
│   ├── search-queries.md
│   └── scoring-rubric.md
└── scripts/
    └── find_candidates.py
```

职责划分：

- `SKILL.md`：入口、触发条件、流程、硬门槛、禁止项、输出要求。
- `references/search-queries.md`：默认 GitHub 搜索模板、topic 组合、重复检查清单。
- `references/scoring-rubric.md`：`值得继续 / 谨慎 / 跳过` 的评分规则。
- `scripts/find_candidates.py`：基础搜索、去重、候选摘要整理。

## 与当前仓的集成

本仓已存在：

- 扫描器：`src/scanner/*.ts`
- 报告 schema：`src/shared/report-schema.ts`
- 报告入口：`public/reports/latest.json`

因此 Skill 不重复实现整套看板逻辑，而是：

1. 在通用模式下做项目发现与筛选。
2. 在检测到本仓时，优先调用现有扫描器或复用现有输出格式。
3. 保证新增 Skill 规则与现有报告字段兼容。

这能减少重复维护，并降低 Skill 与仓内逻辑分叉的风险。

## 验证策略

按照 Skill 编写流程，先做 baseline，再写 Skill。

### baseline 目标

验证“没有 Skill 时”容易出现的失败模式：

- 只看热度，不看可验证性。
- 忽略大项目本地跑不动的问题。
- 忽略重复 PR / 已有 issue 覆盖。
- 为了凑数量放宽推荐门槛。

### Skill 验证目标

- 能稳定产出 5 到 10 个候选。
- 不会把明显跑不动的大项目误判成 `值得继续`。
- 在本仓内调用时，能提示或复用现有看板输出链路。
- 输出的推荐等级与硬门槛一致。

## 风险与取舍

### 保留的复杂度

- 混合型 Skill 比纯仓库绑定型多一层“环境检测与双模式切换”复杂度。

### 主动不做的复杂度

- 不在 Skill 内重复复制整套前端看板。
- 不在 Skill 内直接实现上游 PR 提交流程。
- 不把 Trending / starred 提升为主排序，避免偏离“值得提 PR”的核心目标。

## 自审

- 设计已明确区分“发现项目”和“提交 PR”两个阶段。
- 已把“本地可验证”提升为硬门槛，而不是软建议。
- 已限定大项目例外范围，避免 Skill 重新滑回“只看热度”。
- 已保留本仓看板集成，但未把 Skill 绑死在本仓上。
