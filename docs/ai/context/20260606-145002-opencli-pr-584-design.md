# OpenCLI PR #584 方案记录

## 背景

当前报告预选项目是 `jackwener/OpenCLI`。报告里原本提到的切口是 `opencli douban subject <id>` 查询失败，对应 issue #1851；但上游已经有开放 PR #1854 直接修复该问题，继续提交同类 PR 会变成重复贡献。

因此本轮转向同仓库仍开放、无对应 PR 的 issue #584：`installInterceptor not working after goto a new page`。

## 必须解决的问题

- `Page.installInterceptor(pattern)` 目前只通过 `evaluate()` 在当前 document 里注入 fetch/XHR monkey patch。
- 发生后续导航时，新的 document 不继承这段 patch，导致 `installInterceptor()` 先于 `goto()` 使用的管线场景无法捕获新页面请求。
- issue #584 的携程例子属于该类问题：需要在导航后的页面早期捕获 `batchSearch` 响应。

## 备选方案

### 方案 A：只改携程 adapter 示例

不采纳。上游并没有内置该携程 adapter，且问题出在通用拦截器语义，不应把修复限制在单站点。

### 方案 B：让 `installInterceptor()` 同时注入当前 document 和未来 document

采纳。调用 `installInterceptor(pattern)` 时，保留现有 `evaluate()` 注入，兼容当前页面；如果当前 page 暴露 CDP，则额外调用 `Page.addScriptToEvaluateOnNewDocument`，让后续导航的新 document 自动安装同一拦截器。

### 方案 C：在 `goto()` 内自动重放历史 interceptor

暂不采纳。它需要给 `BasePage` 增加拦截器状态管理，并改变 `goto()` 语义；相比方案 B 范围更大，也更容易影响非 CDP 后端。

## 设计

本轮 PR 只改 `BasePage.installInterceptor()`：

- 生成一次共享 interceptor JS。
- 继续执行 `this.evaluate(interceptorJs)`，保持当前 document 行为不变。
- 如果 `(this as IPage).cdp` 存在，则调用 `Page.addScriptToEvaluateOnNewDocument`，参数 `{ source: '(' + interceptorJs + ')()' }`。
- CDP 注入失败不阻断原有 evaluate 注入，避免非标准浏览器后端或权限缺口导致回归。

测试只覆盖可稳定证明的契约：

- 新增 `BasePage` 单元测试，构造带 `cdp` 的 `ActionPage`，调用 `installInterceptor('batchSearch')`。
- 断言 `evaluate()` 仍被调用。
- 断言 CDP 收到 `Page.addScriptToEvaluateOnNewDocument`，且 source 包含 `batchSearch` 和 `__opencli_xhr`。
- 断言 CDP 抛错时 `installInterceptor()` 仍完成，保留当前兼容性。

## 风险

- 该修复只能保证「安装后发生的导航」会自动注入。用户如果先 `goto(..., { waitUntil: 'none' })`，再安装拦截器，仍可能错过页面最早发出的请求。
- `Page.addScriptToEvaluateOnNewDocument` 会为当前 CDP target 的后续 document 注入脚本；本 PR 不做跨 target、跨 tab 的状态同步，避免扩大范围。

## 验证目标

- 先运行新增测试，确认在修复前失败。
- 修改 `BasePage.installInterceptor()` 后，运行：
  - `npx vitest run --project unit src/browser/base-page.test.ts`
  - `npx tsc --noEmit`
- 如依赖安装或本机环境阻塞，记录具体错误，不伪造通过结果。
