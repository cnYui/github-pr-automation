# 主控仓库工作区同步设计

## 目标

处理主控仓库根工作区内全部已修改和未跟踪内容，完成本地提交，并与 `cnYui/github-pr-automation` 的 `main` 分支同步。

## 当前事实

- 本地当前分支为 `main`，与 `origin/main` 无领先或落后提交。
- `origin` 已指向现有私有仓库 `https://github.com/cnYui/github-pr-automation.git`，因此不重复创建同名仓库。
- 待处理内容由日报 JSON、构建目录中的对应日报、运行与巡检上下文文档、项目记忆组成。
- `public/reports/` 与 `dist/reports/` 中同名日报内容一致，`latest.json` 与 2026-07-14 日报一致。
- 未发现空文件、无效 JSON 或疑似 GitHub token、API key、密码、私钥内容。

## 边界

- 纳入根仓库 `git status` 展示的全部业务记录、报告和项目记忆。
- 保持 `.gitignore` 现有边界，不纳入 `work/`、`data/`、`outputs/`、`node_modules/`、环境文件、日志和缓存。
- 不处理 `work/` 下外部候选仓库的独立 Git 状态，它们不是主控仓工作区的一部分，也不能混入主控仓提交。
- 不创建 PR；用户要求的是主控仓本地与远端直接同步，且当前就在 `main`。

## 方案

1. 先完成内容、敏感信息、JSON 一致性和远端状态检查。
2. 新增本次设计、计划和执行记录，并把关键决策写入 `AGENTS.md`。
3. 运行全量测试、类型检查、构建及差异检查。
4. 明确列出根工作区全部待提交文件后统一暂存，复核暂存差异。
5. 使用清晰的维护类提交信息提交到本地 `main`。
6. 推送 `main` 到已有的 `origin`，再核对提交 SHA、远端默认分支和工作区状态。

## 取舍

本次改动跨越多次自动化运行，通常应按运行拆分提交；但用户明确要求处理当前全部未提交和未跟踪内容，而且这些内容都属于同一主控仓运行记录与报告同步，因此采用一次维护提交，避免留下部分历史仍未同步。
